# Синхронизация

> Статус: **метаданные и файлы — готово** (этап 7). Стриминг по LAN и
> удалённое скачивание через ПК — следующий шаг (7б).

Одна библиотека на ПК и телефоне — лайки, плейлисты, история и сами треки.
Без сервера и аккаунтов: устройства общаются напрямую в локальной сети.

## Как пользоваться

1. ViPlayer открыт на обоих устройствах, оба в одной Wi-Fi-сети.
2. **Настройки → Синхронизация**: второе устройство появляется в «Устройства рядом».
3. «Связать» → на втором устройстве показывается 6-значный код → ввести его.
4. Дальше синхронизация автоматическая: при появлении устройства в сети (не чаще
   раза в минуту), через 10 с после изменений и по кнопке «Синхронизировать».

Если устройства не видят друг друга (роутер блокирует широковещание) —
«Подключить по адресу» и ввести адрес, показанный на другом устройстве.

### Брандмауэр на ПК

Входящие соединения должны быть разрешены для портов ViPlayer:
**UDP 48125** (обнаружение) и **TCP 48126** (обмен данными). Для ufw:

```bash
sudo ufw allow from 192.168.0.0/16 to any port 48125 proto udp
sudo ufw allow from 192.168.0.0/16 to any port 48126 proto tcp
```

(подставьте свою подсеть, если она не `192.168.x.x`).

## Что синхронизируется

| Данные | Как |
|---|---|
| Треки (метаданные), лайки, плейлисты, история | изменения в обе стороны |
| Файлы: телефон → ПК | ПК забирает **все** треки, которых у него нет |
| Файлы: ПК → телефон | «Понравившееся» и плейлисты с флагом **«Доступен офлайн»**; переключатель «Копировать всю новую музыку» |
| Папки, пути, настройки, сопряжения | **не** синхронизируются — свои на каждом устройстве |

Файлы забирает тот, кто запустил синхронизацию; запускают её оба устройства, поэтому
каждое получает своё. Полученный файл кладётся в папку загрузок и сразу попадает
в медиатеку (к уже известному треку — по отпечатку).

## Как устроено

`lib/core/sync/`:

| Файл | Роль |
|---|---|
| `discovery.dart` | UDP-маяк `VP1\|id\|порт\|тип\|имя` каждые 3 с; устройство «пропадает» через 15 с тишины |
| `sync_service.dart` | HTTP-сервер (порт 48126) и клиент: сопряжение, обмен изменениями, файлы |
| `changeset.dart` | сборка «изменений после ревизии N» и их слияние |
| `sync_auth.dart` | код сопряжения, общий секрет, подпись запросов |
| `peer_store.dart` | связанные устройства и имя этого устройства (локальные настройки) |
| `sync_providers.dart` | запуск, Android multicast lock |

### Ревизии (что отправлять)

У синхронизируемых таблиц есть локальная колонка `local_rev`. **Триггеры SQLite**
ставят в неё следующее значение общего счётчика при каждой вставке/изменении —
включая строки, пришедшие с других устройств (так изменения идут дальше, на третье
устройство). Ни один путь записи в коде не может «забыть» отметить изменение.

Обмен A → B:

1. A: `GET /changes?since=<ревизия B, до которой A уже всё получил>` → применяет;
   в ответе B сообщает, до какой ревизии A он уже получил (`X-VP-Cursor`).
2. A: `POST /changes` — свои изменения после этой ревизии.
3. A: `GET /files` → скачивает нужные `GET /file/<trackId>`.

Все изменения после курсора идут одним пакетом (без постраничной разбивки), поэтому
строка никогда не приходит раньше строк, на которые ссылается.

### Слияние

- Побеждает более позднее изменение строки (`updated_at`); при равенстве — строка,
  чей JSON «больше»: оба устройства выбирают одно и то же.
- Удаление — «надгробие» (`deleted = true`), сливается как обычное изменение.
- Порядок в плейлистах — дробные позиции: перемещение меняет одну строку.
- **Одна песня, найденная на двух устройствах независимо** (один отпечаток, разные
  id), становится одним треком под **меньшим** id на обоих устройствах; файлы,
  записи плейлистов и история переносятся на него. Старый id запоминается
  (`track_aliases`), и строки, которые ещё ссылаются на него, попадают куда нужно.

### Опознание трека

Отпечаток: нормализованные «исполнитель + название» + длительность с шагом 3 с
(`core/library/fingerprint.dart`). Пути файлов в синк не попадают.

### Безопасность

- Сопряжение: одно устройство показывает код, на другом его вводят. Оба выводят
  общий секрет из кода и id устройств; **сам код по сети не передаётся**. Код живёт
  2 минуты и сгорает после 5 неверных попыток.
- Каждый запрос (кроме сопряжения) подписан HMAC-SHA256 от метода, пути и времени;
  запросы старше/новее 5 минут отклоняются (защита от повтора). Несвязанные
  устройства получают `401`.
- **Ограничения:** трафик не шифруется; записанный обмен сопряжением теоретически
  можно перебрать офлайн (6 цифр). Модель угроз — домашняя сеть: связывайте
  устройства в доверенной сети.

## Следующий шаг (7б)

- **Стриминг по LAN:** дома телефон слушает треки ПК без копирования.
- **Удалённое скачивание:** телефон отдаёт ссылку/поиск ПК (yt-dlp), результат
  приходит синком — обход ограничения YouTube на телефоне (см. DOWNLOADS.md).

## В будущем: синхронизация через интернет без своего сервера

и тот же формат изменений):

- Позже — небольшой собственный relay-сервер.
